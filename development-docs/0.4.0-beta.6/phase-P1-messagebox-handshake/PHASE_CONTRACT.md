## 1. Goal

Hodos's PeerPay notices reach MessageBox again, and incoming PeerPay is picked up again; the BRC-103 client (`AuthFetchClient`, used for MessageBox) refuses a handshake reply that is not signed by the server it names.

## 2. Done means

- [ ] The handshake `initialNonce` is 48 bytes: 16 random bytes ‖ HMAC-SHA256 under `[2,'server hmac']`, `keyID` = the WHATWG `TextDecoder` (replacement mode, BOM stripped) decoding of those 16 bytes, counterparty self. Byte-identical to `@bsv/sdk` 2.8.11 `createNonce` on fixed vectors (`P1-A1`).
- [ ] The per-request `x-bsv-auth-nonce` and `x-bsv-auth-request-id` stay 32 bytes (`P1-A2`).
- [ ] The handshake reply is accepted only if `messageType` is `initialResponse`, `yourNonce` equals the nonce we sent, `identityKey` is a valid compressed key, and `signature` verifies over `ourNonce ‖ serverNonce` under `[2,'auth message signature']`, keyID `"<ourNonce> <serverNonce>"`, counterparty = that key (`P1-A3`, `P1-A4`).
- [ ] Live: the dev wallet's PeerPay poll gets `listMessages` 200 from `messagebox.babbage.systems`; one fresh PeerPay is sent and its notice delivered, and received by the recipient wallet (`P1-A5`).
- [ ] The live `listMessages` response shape is recorded, and our parser handles it: no messages silently dropped because of paging (`P1-A6`).

## 3. Invariants preserved

| ID | Invariant | Why this phase could break it |
|---|---|---|
| `R-PEERPAY-DELIVERY` | A PeerPay delivers its message or never leaves the wallet | This phase changes the handshake every delivery depends on. The new verification could refuse a legitimate server (false negative) and turn "delivered" into "queued forever" |
| Invariant 3 (crypto) | Signing/derivation unchanged without approval | Approved: the handshake nonce and the reply-signature check are new crypto calls. **No existing derivation or signing function is modified**; only callers are added |

## 8. Pre-mortem

| Failure story | Caught by |
|---|---|
| `keyID` decoding differs from `TextDecoder` for some byte pattern, so a server that verifies our nonce (none today) or our own echo check would fail 1 time in N | `P1-A1` vectors include invalid-UTF-8 and BOM cases |
| The verification rejects MessageBox's genuine reply (high-S signature, number-array vs base64 signature, nonce order) ⇒ every delivery fails again, silently queued | `P1-A3` uses an SDK-produced reply; `P1-A5` live; normalize-S before `verify_ecdsa` (the SDK accepts any `s` in (0,n)) |
| The fix works but paging drops messages | `P1-A6` |
| The old queued notices flood out on the first successful poll | Outbox rows are `exhausted` (no auto-retry); recorded in `P1-A5` |

## 12. Open questions for the owner

1. ❌ **RETRACTED 2026-09-30 — no divergence in our HMAC endpoints.** I reported that `/createHmac` and `/verifyHmac` differ from the SDK for ~1 key in 256. The **SDK half is measured and true**: when the shared secret's x-coordinate starts with `00`, `@bsv/sdk` keys the HMAC with the 31-byte minimal form (keyID `k16`: SDK HMAC == 31-byte key, ≠ 32-byte key; `../g2-validator/lz_check.mjs`). The **Hodos half was never checked**: `handlers.rs :: create_hmac` and `verify_hmac`, and `certificate_handlers.rs :: create_nonce_with_hmac`, already strip leading zeros (`hmac_key_stripped`), which is Rule 2 in `rust-wallet/src/crypto/CLAUDE.md`. The claim came from the review agent's "may have the same divergence; I did not check it" and was passed on without reading the code. 👤 The owner approved a fix before the retraction; **no fix is needed** and none was made. This phase's nonce helper strips the same way (it duplicates the rule inline rather than sharing a helper).
2. **Duplicate nonce code, not changed:** `handlers/certificate_handlers.rs :: create_nonce_with_hmac` (certificate issuance) makes the same nonce; it strips the leading zero but does **not** strip a leading BOM (`js_to_utf8` = `from_utf8_lossy`), so ~1 nonce in 16.7M differs from the SDK's. It only matters if a certifier verifies our nonce (they verify their own). Reported, not changed (rule 3).
3. **Fixed on the way (one line, in the function this phase changes):** `AuthFetchClient::fetch` dropped an explicit port when building the handshake URL, so a BRC-103 server on a non-default port got its handshake on the default port. MessageBox (443) was unaffected; `P1-A2`'s wire test found it.
