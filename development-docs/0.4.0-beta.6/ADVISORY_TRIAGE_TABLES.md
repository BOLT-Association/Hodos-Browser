## Top concerns

1. **TSA-023 + TSA-044: `abortAction` can un-spend a broadcast transaction.** Only `Confirmed` is refused. An `unproven` (broadcast) or `sending` action can be aborted, and `release_unbroadcast_transaction` then restores its inputs to `spendable=1`, swallowing errors with `unwrap_or(0)` and still returning `aborted:true`. That is a candidate working-rule-7 trip-wire 1 and 2. Code-reading only: verify with a unit test on a DB fixture before escalating.
2. **TSA-042: `signAction`/`abortAction` references are not bound to the originator.** Any approved origin that has `action-<uuid>` can finalize/broadcast or abort another site's action.
3. **TSA-061: strict result validation in upgraded `@bsv/sdk`.** This is the most likely next "our client broke though our code didn't" event, since dApps reach Hodos via `window.CWI`. Run Hodos's response shapes through the new validator now.
4. **TSA-040 (+021/022): `/verifyHmac` and `/verifySignature` resolve `{valid:false}` instead of throwing.** Unfixed dApp code that relies on the SDK's throw semantics accepts forgeries only inside Hodos. Confirm the SDK contract in `reference/ts-stack` first.
5. **TSA-047 (+041): MessageBox delivery/recipient fees.** Hodos never attaches a fee payment. Once the 48-byte nonce fix lands, fee enforcement may be the next PeerPay-send rejection, and our outbox would retry it as transient.
6. **TSA-051: paymail sender identity.** We send `senderHandle = "<name>'s Hodos Wallet"` (not a handle) unsigned. On P2P the receive-tx notify happens **after** broadcast, so a hardened receiver's rejection leaves the recipient's wallet unaware of a real payment.
7. **TSA-010: identity binding.** Three analogs: AuthFetch never verifies the server identity (ticketed); the local BRC-33 relay trusts the unsigned `x-bsv-auth-identity-key` header; cert issuance proceeds when the server identity ≠ the requested certifier.
8. **TSA-057: headerless loopback requests trusted as the wallet UI.** Same class as the advisory; already ticketed in `0.4.0-beta.8/tickets/`.

No P0: nothing in this chunk showed code-level evidence that users are broken today or that funds or identity are being lost now. The already-known P0 (MessageBox's 48-byte `initialNonce`, `TICKET_messagebox_rejects_our_auth_handshake_since_2026_09_23.md`) is not attributable to any item in this chunk.

## Top concerns

1. **TSA-120 (P0): BRC-103 nonce and field bounds. This is breaking users now.** Our 32-byte `initialNonce` (`authfetch.rs :: generate_nonce_base64`) is what MessageBox rejects, so PeerPay send and receive are down. When fixing it, also check the wallet's **own** `well_known_auth` 32-byte server nonce, which hardened TS clients may now refuse. The client also never verifies the server's handshake signature.
2. **TSA-066 (P0 candidate, code reading only): certifierUrl lets an approved dApp point the wallet at itself.** `acquire_certificate_issuance` POSTs to an unvalidated, redirect-following `certifierUrl`. Its header-less loopback request is trusted as first-party, and `/wallet/delete` and `/shutdown` ignore their bodies. Per rule 7, confirm cheaply with a harmless loopback target before escalating. This is a third caller the untracked headerless-loopback ticket does not list.
3. **TSA-121 (P1): the BRC-121 paid retry follows redirects with payment headers, accepts http payees, and the paid-content cache is URL-keyed, not opt-in, and never expires.**
4. **TSA-082 and TSA-065 (P1): hardened SDK clients now verify wallet results and templates exactly.** Hodos's extra 1000-sat service-fee output, and its createAction result shape, could make upgraded dApps reject every action. This needs one offline interop run against the ts-stack `b3155fa2` validators.
5. **TSA-063 (P1): the HTTPWalletJSON strict decoder and error-envelope validation against our non-BRC-100 error bodies and extra createAction fields.** Testable without money.
6. **TSA-077 (P1): IdentityResolver shows certificate identities without checking the signature, lock or subject**, and that feeds payment-recipient naming.
7. **TSA-073 (P1): SHIP advertisements are not authenticated and any `http*` host is accepted**, which is the same confused-deputy shape as TSA-066 through on-chain data.
8. **TSA-069 (P1): createAction does not range-check output satoshis** (negative, over 21e14, i64 overflow). No theft is expected, but it can leave money-path rows for a tx that can never mine.

## Top concerns

- **TSA-131 (P0): MessageBox rejects our handshake.** `authfetch.rs :: generate_nonce_base64` sends a 32-byte `initialNonce`, and the server now requires 48. PeerPay over MessageBox has been broken since 2026-09-23. The fix is the handshake's initial nonce only; the per-request nonce and request-id stay 32. Already ticketed. Open question: whether hardened TS peers now also reject our **responder's** 32-byte random nonce in `handlers.rs :: well_known_auth`.
- **TSA-132 (P1): peer identity is not verified or pinned.** `AuthFetchClient::handshake` checks neither the server's initialResponse signature, nor the nonce echo, nor MessageBox's identity key. The acquireCertificate client logs "TypeScript SDK would reject this" on a certifier/responder identity mismatch and then carries on. The second case is reachable from any dApp-chosen certifier URL.
- **TSA-148 (P1): createAction output amounts are not range-checked.** `CreateActionOutput.satoshis: Option<i64>` accepts negative values. They flow into funding arithmetic and `TxOutput`, and on noSend into basket-output DB rows. That DB write is a working-rule-7 trip-wire-1 shape: verify it cheaply before treating it as live.
- **TSA-141 (P1): the spending-cap price can be pushed to zero.** `PaymentCost.h :: ExtractOutputSatoshis` (and Rust's defence-in-depth sum) add output amounts with no overflow or negative check, so a body can price at about 1 sat and pass the cap silently. The resulting tx appears consensus-invalid, so this is a gate-integrity defect, not a demonstrated loss. Fix it together with 148.
- The P2 group, for the record:
  - BRC-103 responder hygiene: no nonce consumption, unbounded sessions, replayable initialRequest (124/128/134).
  - http allowed for BRC-103 and certifier URLs (127).
  - NaN passes `validate_price` (137).
  - `purge_expired_approvals` has no production caller (142).
  - No response byte caps and default redirects on provider/overlay fetches (155/176).
  - Unsigned SHIP host adverts steer our POSTs (176).
  - `/isAuthenticated` always returns true (167).

## Top concerns

- **TSA-188 → P1: the proven-tx table can be poisoned.** `handlers.rs :: cache_arc_merkle_proof` writes ARC's BUMP into the immutable `proven_txs` table without a merkle-root check, keyed by the txid the *provider* returned. Separately, `task_check_for_proofs` stores proofs "anyway" when the header fetch fails. Both are durable state that later BEEF building reads (working-rule-7 trip-wire 3, pending a cheap chain check of existing rows).
- **TSA-192 → P1: a broadcast acknowledgement can confirm the wrong transaction.** In `broadcast_transaction`, a mismatched txid is accepted whenever a merklePath is present. With `MINED`, *our* transaction is then marked `confirmed` on the strength of another transaction's acknowledgement.
- **TSA-221 → P1: identity-cert publish/unpublish can be spoofed.** SHIP advertisements are never verified (`parse_ship_advertisement`, which has a "skip for now, used for verification" comment). A forged host joins the `tm_identity` submit set, and `submit_to_topic` returns success on the first host that admits. So an **unpublish** can report success while the certificate stays public. TSA-198, -207, -223 and -224 are all fixed by the same change: verify ads the way the SDK does, and require public HTTPS.
- The P2s, lower priority, fall into two fixes:
  - TSA-189, -225 and -227: add a no-redirect policy, body caps and txid correlation to the provider clients.
  - TSA-229: all header and merkle-root trust rests on one WoC JSON field, and no header or PoW is validated.

## Top concerns

1. **TSA-260 — abortAction** (P0 pending a cheap unit test). `abort_action` re-locks `state.database` while holding the guard. 3. **TSA-250 — weak ARC statuses count as "on chain".** `RECEIVED` / `STORED` / `QUEUED` / `ANNOUNCED` map to `InMempool`, so `internalize_action` accepts incoming BEEF as on-chain. That contradicts the project's own ARC ladder rule. This is on the money-in path.

6. **TSA-283 — IdentityResolver labels any identity key with any overlay certificate's name.** Subject is not compared and the signature is not verified, in the Send / recipient-resolve UI.
7. **TSA-261 — sendWith is not all-or-nothing.** Main tx first, then each member independently; failures `continue`.
8. **COMPAT (TSA-272 / 274 / 278) — the next MessageBox-style silent break.** A hardened SDK `WalletClient` validates *Hodos's* results. Three likely rejection points: `listActions` returns legacy status strings and extra keys; `listOutputs` BEEF can omit transactions; `createAction` adds a service-fee output. ## Top concerns

- **TSA-401 (P1): a dApp might refuse transactions Hodos signs (compat unknown).** The new ts-sdk "bound-action" primitive checks the final transaction against the request, including outputs, version, locktime and sequences. Hodos always adds a 1000-sat service-fee output the dApp never asked for. If the verifier treats any unrequested non-change output as substitution, dApps that adopt it will reject Hodos transactions. This is the same "hardening upstream breaks our unchanged client" shape as the MessageBox nonce. To settle it, read the verifier source and run one Hodos createAction/signAction result through it.
- **TSA-374 / TSA-417 / TSA-420 (P2, one root cause): our BRC-103 client authenticates in one direction only.** It signs its requests. It never verifies the server's handshake or response signatures, never pins the server identity, follows redirects while carrying `x-bsv-auth-*` headers, and has no response size cap. Worth fixing alongside the 48-byte nonce change, since that change touches the same function.
- **TSA-415 (P2, money path): an ARC reply can count as a successful broadcast when it shouldn't.** An HTTP 200 with an unknown or empty `txStatus` is treated as success, and the txid binding has holes (an empty returned txid passes; a mismatched txid passes when a merkle path is present).
- **TSA-381 / TSA-382 (P2): the Paymail client trusts the host too much.**
  - A host-controlled avatar URL is rendered as an image in the wallet UI, and the profile URL is fetched with no https or non-local check.
  - Separately, we found our own capability-confusion bug: the basic `paymentDestination` falls back to the P2P receive-transaction capability ID.
- **TSA-412 (P2): overlay hosts from SHIP ads are accepted without checks.** Any `http*` URL is taken, including plain http and local hosts, and the advertiser signature is never checked.
- **TSA-424 (P2): a warn-level log line can write PeerPay token contents to production logs.**

## Top concerns

1. **The recipient-name resolver trusts overlay data with no checks** (5vmp F8d). `identity_resolver.rs` does not verify the certificate signature, does not enforce the certifier allowlist, and in `resolve()` does not check that the certificate's subject is the key that was asked about. In the send flow's name search, a malicious or compromised overlay can map a trusted name to an attacker's key. That spoofs the recipient of a real payment. **P1.**
2. **Certificate signature checks are skipped when `revocationOutpoint` is a placeholder** (5vmp F8a/b). This applies to both direct and issuance acquisition, so a dApp can plant a certificate claiming any certifier; it can then be listed, proved and published. Track-5 P1 does not cover this skip; it covers only the missing handshake signature. **P1.**
3. **The local message-relay endpoints trust an unsigned identity header** (2qqx analogue). `/listMessages`, `/acknowledgeMessage` and `/sendMessage` take `x-bsv-auth-identity-key` as fact and verify no signature. Whether web content can set that header through the interceptor is UNKNOWN. If it can, any approved site can read or delete messages addressed to any key held in the local relay. **P2**, or P1 if the header reaches the handler from a page.
4. **SHIP advertisements are accepted without signature checks and may name plain-HTTP hosts** (5vmp F7/F4 analogue). This feeds concerns 1 and 2, because it chooses which overlay hosts we trust. **P2.**
5. **`certifierUrl` is not restricted to HTTPS or to non-loopback hosts** (5vmp F4 analogue). **P2.**
6. **No compatibility breakage was found in any of these five advisories** (all A = NO). Two items would be worth confirming live when the owner next makes a paid request: the 402-pay 0.3.0 strict Atomic BEEF rule (our envelope reads as compliant), and ARC enforcing MUST_USE_FORKID (all our sighashes are 0x41).
7. Already scheduled, restated for completeness: AuthFetch does not verify the server's identity (`TICKET_brc103_server_identity_unverified.md`, track-5 P1), and the issuance handshake "proceeding anyway" when the signature is absent (P1-A3).
